# 10 — Core Design

How the core of `cydui` works as of iteration 1. Requirements are in `01`/`02`; this document records the decisions and the numeric conventions that the tests pin down.

## Layers
```
 app code ──▶ cydui_draw_*()  ──▶ command list (fixed array) ──▶ cydui_raster_strip() ──▶ backend->flush_strip()
              (ctx.c)              (cmd.h)                        (raster.c)                (mem, sdl, esp32)
```
The core (`src/`, `include/`) is C99 and depends on nothing but `stdint.h`, `stddef.h`, `stdbool.h` and `string.h`. Backends are separate libraries: `backends/mem` (framebuffer in RAM, hash, PNG), `backends/sdl` (window and mouse); `backends/esp32` arrives in It5.

## Memory (FR-01, NFR-11, NFR-12, CT-01)
- The library never calls `malloc`; the local check script checks that `libcydui.a` has no reference to it, and no writable global or static data (NFR-21).
- `cydui_init` receives two blocks from the caller: memory for the command list and memory for the render strip. The command list takes as many whole `cydui_cmd` as fit; the strip height is `strip_mem_size / (width * 2)`, capped at the screen height. Too little memory returns `CYDUI_ERR_NO_MEMORY` instead of failing later.
- `cydui_arena` is the bump allocator used for that carving. It aligns the address (not the offset), rejects zero sizes and non-power-of-two alignments, and cannot wrap on huge sizes.
- Overflow of the command list drops the command and sets `CYDUI_ERR_CMD_OVERFLOW`; the frame still renders. Commands that would draw nothing (empty, fully clipped, alpha 0) are dropped *before* the capacity check, so they cost nothing.

## Commands (FR-02)
`RECT`, `RRECT` (filled, or an outline drawn inside the rectangle), `LINE`, `BITMAP` and `GRADIENT`. Every command stores `alpha` (0..255), its geometry and the clip rectangle in effect when it was emitted (the clip is already intersected with the screen). The list is rasterized in order (painter's algorithm).

- **Bitmap formats:** `RGB565` (2 bytes per pixel, native order, row-major) and `A4` (4-bit coverage, high nibble first, rows padded to a whole byte; tinted with a color). `A4` is what bitmap fonts will use in It2.
- **CT-10:** `cydui_draw_bitmap` takes the buffer length and drops the command with `CYDUI_ERR_BAD_BITMAP` if it is smaller than `w * h * bpp` (computed in `size_t`; the largest legal bitmap, 32767 x 32767, is rejected cleanly instead of wrapping). The caller must keep the data alive until `cydui_end_frame`.
- **Limits:** radius and line thickness are `uint8_t` (0..255). Radius is clamped to half the smaller side. An outline thicker than the shape degrades to a filled shape.

## Rasterization (FR-03, FR-04, FR-06, NFR-30)
- **Strips.** `cydui_end_frame` renders the screen in full-width strips and hands each to `backend->flush_strip`. A strip is first filled with the frame's clear color, then every command that touches it is drawn. **The image does not depend on the strip height** — this is tested with heights from 1 to 240 (unit tests, goldens) and fuzzed.
- **Integers only.** No `float`/`double` anywhere in the core, so the output is bit-identical across gcc, clang, `-O0`/`-O2` and (by design) the ESP32. The goldens are pinned by gcc and verified on clang and on an optimized build.
- **Color.** `cydui_color` is RGB565 in native byte order; byte swapping for a panel is the backend's job. `CYDUI_RGB(r,g,b)` packs 8-bit channels.
- **Blending.** Source-over using the spread-bits trick (`0x07E0F81F`): 5-bit alpha granularity (`(alpha + 4) >> 3`), exact at alpha 0 and 255. Antialiasing coverage in 1/16 units is combined with the command alpha and applied through the same blend; a coverage near 0 is skipped and near 1 is written directly.
- **Antialiasing.** Signed distance in 1/16 pixel with an integer square root. Pixel centers sit at `(x*16 + 8)`, so integer-aligned straight edges are crisp and only curves need AA. Coverage is `clamp(8 - d, 0, 16)` (half a pixel on each side of the edge).
  - *Rounded rect:* only the corner zones compute a distance; body rows are solid spans. An outline is the outer coverage minus the coverage of the rectangle shrunk by the thickness (radius reduced accordingly). A row is cut into runs at the edges of the corners and of the inner shape; a run has one coverage (computed once and filled), and only the pixels of an arc are computed, and of those only the ones within half a pixel of it need the square root (the others are decided by comparing the squared distance with `(R ± 8)²`).
  - *Line:* distance from the pixel to the segment, with round caps; endpoints are pixel centers, so a 1 px horizontal line covers exactly one row. Thickness is the stroke width in pixels. Uses `int64_t` for the projection and cross product; pixels beyond `thickness/2 + 1/2` px are rejected before any division, and each row only visits the columns of the capsule round the segment (a superset taken with integer divisions, where the exact test decides).
  - *Speed (It7).* Every fast path only skips work whose result is known, so the output is the one of the plain version (a differential test against the previous rasterizer on 400000 random strips, and the goldens, decided it): `span_put` fills an opaque run by words and blends a translucent one once per distinct background; a glyph skips empty bytes (two pixels per test) and uses a table of 16 alphas; the 565 blend is one inline function shared with `cydui_blend` (`src/blend.h`). On the board a full frame draws in 11.5 ms instead of 26.
  - *Verified against geometry:* the tests sum the coverage of a rounded rect, a circle and a thick line and compare with the exact area (`w*h - (4-π)r²`, `πr²`, `L*t + πt²/4`) within ~0.3%, so the AA is correct and not only symmetric.
- **Gradient.** Two colors, per-channel integer interpolation with truncation, exact at both ends; a one-pixel-long gradient is the first color.

## Text and fonts (FR-10..13, CT-02, CT-03, CT-04, AB-16)

**Font format** (`include/cydui/font.h`). A `cydui_font` is constant data: a glyph table sorted by code point, 4-bit coverage bitmaps (A4, high nibble first, rows padded to a byte) and the line metrics. Lookup is a binary search that falls back to the box glyph stored under U+FFFD. Advances are whole pixels and there is no kerning (a known limitation, see below).

**Making fonts.** `tools/fontgen.py` renders a TTF with FreeType (`freetype-py==2.5.1`, which bundles FreeType 2.13.2, so output does not depend on the system library) into 8-bit coverage, quantizes it to 4 bits, always generates its own hollow box as the fallback glyph, shares storage between identical bitmaps, and writes `OUT.c`/`OUT.h` deterministically: `tools/gen_fonts.sh --check` regenerates into a temp dir and compares byte for byte. The bundled `cydui_sans_{12,16,24}` use ASCII, Latin-1 and a few symbols (`• … € ← ↑ → ↓`). `--preview TEXT` prints ASCII art of a string set in the generated font, for a quick look without a display.

**Licensing.** The bundled fonts are renderings of Liberation Sans and stay under the SIL OFL 1.1 (`fonts/LICENSE-OFL.txt`), not the MIT license of the code. The OFL reserves the name "Liberation", so the generated fonts are called `cydui_sans_*`; each generated file carries the original copyright notice and the OFL notice.

**UTF-8** (`include/cydui/utf8.h`). `cydui_utf8_decode` is strict: overlong forms, surrogates, values above U+10FFFF and bytes that never occur in UTF-8 are ill-formed, and each ill-formed sequence gives one U+FFFD for its "maximal subpart" (so `E2 82` followed by `g` is one replacement, `F0 80 80 80` is four). It always consumes at least one byte and never reads past `len`.

**Drawing text.** `cydui_draw_text` copies the string into a per-frame text arena (`text_mem` in the config), so callers may pass temporary buffers, and records one `CYDUI_CMD_TEXT`. Without `text_mem`, or when it is full, the text is dropped and `CYDUI_ERR_NO_MEMORY` is raised (CT-01). The rasterizer lays the text out again for every strip and blits only what touches it, so the image does not depend on the strip height. `cydui_text_size` measures with the same layout code, so a box sized from it always fits what is drawn.

**Layout.** One linear pass over the code points. Lines break at `\n`; at the last run of spaces when the text would pass the wrap width; and inside a word wider than the line. Every line consumes at least one byte, so the loop always ends even for a box narrower than one glyph. Leading spaces are kept (an indent); a run of spaces at a wrap point is dropped; trailing spaces do not count towards the width. A final newline does not add an empty line. `\r` is skipped and has no width.

**Limits (CT-02).** At most `CYDUI_MAX_STR` (256) bytes of a string are used. The cut falls on a character boundary: a sequence the limit would split is dropped whole, and `CYDUI_ERR_TEXT_TRUNCATED` is raised (informative, the text is still drawn). For `CYDUI_NTS` strings the search for the NUL stops at the limit, so an unterminated buffer is never read beyond it.

**Control and bidirectional characters (CT-04).** These draw the fallback box even when the font has a glyph for them: C0 and C1 controls (including tab and DEL), U+061C, U+200E/200F, U+202A..202E and U+2066..2069. The set is wider than the two ranges written in CT-04 (it adds the marks and the C0/C1 controls); the bidi part can be compiled out with `CYDUI_FILTER_CONTROL=0`. Boundaries are tested with real glyphs on both sides of every range.

**Malformed fonts (AB-16, CT-09).** The glyph bitmap is read only through `cydui_font_glyph_data`, which checks `offset + size <= bitmap_len` without overflow; the fallback index is checked before use; a font without a usable fallback is rejected (`CYDUI_ERR_BAD_ARG`). `cydui_font_validate` does the full check (order, bounds, fallback, metrics) for startup and tests. Culling uses `CYDUI_TEXT_REACH`, the worst-case distance of a glyph's ink from its line box (`ascent + 383`, from the int8 bearings and 255-row bitmaps), so skipping a line or a command can never change the image whatever the font says. A fuzz-built font with a tall ascent over a short line exposed exactly this once.

**Measured on the ESP32 (Xtensa, `-Os`, 32-bit pointers).**

| Item | Size |
|------|------|
| Whole core (`arena ctx font raster text types utf8`) | 6.8 KB of code (budget NFR-50: 60 KB) |
| `cydui_sans_12` / `_16` / `_24` | 9.3 / 13.1 / 23.4 KB (45.7 KB for the three; R-07) |
| `cydui_cmd` | 36 bytes (a list of 64 commands: 2.3 KB) |
| `cydui_ctx` / `cydui_font` / `cydui_glyph` | 52 / 20 / 16 bytes |

The line rasterizer uses `int64_t`, which the 32-bit core emulates; it is still to be timed on the board (R-02, It5).

## Immediate-mode UI (FR-20..24, FR-30, FR-40, FR-41, CT-02, CT-05, CT-07, CT-11)

`include/cydui/ui.h` and `theme.h`, `src/{ui,layout,widgets,theme,scroll}.c`. `cydui_ui` wraps the `cydui_ctx` (the rasterizer is untouched) and adds ids, a state table, input, layout and the widgets. The application calls the widgets again every frame:

```c
while (cydui_ui_begin(&ui, clear)) {      /* polls input, opens the frame; false once QUIT arrived */
    if (cydui_button(&ui, "Add")) add();
    cydui_ui_end(&ui);                     /* closes containers, renders; true = "draw another frame soon" */
}
```
`CYDUI_STORAGE(name, w, h, strip_rows, cmds, text_bytes, state_entries)` declares all the memory as one static object and `CYDUI_CONFIG(name, backend, &theme)` builds the config over it, so `examples/hello` is 22 lines (NFR-40, checked by a test). The library still never allocates.

**Ids and state (CT-07).** An id is a 32-bit FNV-1a hash of the label mixed with the ids pushed by `cydui_push_id_*`, plus a 16-bit check computed by a different function (sdbm style), so two labels that collide in the hash stay apart in the state table. Both are pinned in the tests against values computed independently. `"Done##3"` shows "Done" and hashes the whole string, so a list needs no `push_id`. Containers do not scope ids: the same label twice in one frame collides wherever it is, and in debug builds (`CYDUI_DEBUG_IDS`) a per-frame set flags it with `CYDUI_ERR_ID_COLLISION`. The state table has a fixed size in caller memory and is searched linearly (a few dozen entries; hashing would only add code). Entries not looked up for `CYDUI_STATE_TTL` (120) frames are recycled by a sweep of at most 8 entries per frame; when the table is full the entry unused for longest is replaced, never the active widget's, and with no memory at all widgets simply have no state. Containers use it to remember their `fill` numbers and, when they place their children, their size; scroll areas keep their offset, speed and content height in it. An entry is 32 bytes (`a`..`d` belong to whoever owns the id); animations will use it too.

**Input (FR-40, FR-41, CT-05, CT-06).** `cydui_ui_begin` polls the backend (at most 64 events) into a queue of 32. Consecutive MOVEs merge; when the queue is full the oldest MOVE is dropped first and then the oldest event, so the newest state always survives. At most 16 events are processed per frame, coordinates are clamped to the screen and unknown event types are ignored. The pointer state machine copes with disorder: a release without a press is ignored, a press while one is held cancels the old one, and at most one press edge and one release edge are taken per frame (a second press waits for the next frame).
- *Tap:* press and release on the same widget, within the tap slop (a distance, 10 px by default: exactly 10 is a tap, 11 is not) and without turning into a long press. Travel that comes back to the start does not undo a drag.
- *Long press:* the pointer held still for `long_press_ms` (500); it fires once, also when the release arrives in a frame that came late, and unsigned subtraction keeps it right across the 32-bit clock wrap. Without a clock (`now_ms == NULL`) it never fires.
- *Owner of a press:* the first widget, in call order, whose rectangle cut by the clip contains the point where the press **started**; a press has one owner even when it ends in the same frame; a disabled widget does not capture it. `cydui_interact` returns `pressed`, `clicked`, `long_pressed`, `dragging`, `released` and the drag delta, and is public and stable (it is the base of custom widgets, `docs/11-api.md`): `CYDUI_CAPTURE` makes a widget keep the press whatever the pointer does (the slider), and the response carries the pointer position for the owner of the press.
- `cydui_ui_end` returns true while a press is held (so a long press can fire in an app that redraws on demand), while events wait, and while the layout is still settling.

**Layout (FR-23, FR-24, R-05).** A cursor model: a container places its children one after the other and a position is final the moment a widget is placed, so hit-testing happens in the same frame. The gap goes *before* each child, so `cydui_set_spacing` takes effect at once. Rows go left to right (children's tops aligned unless the container says otherwise, see below), columns (and the screen, which has a margin of one spacing) top to bottom, grids fill rows of equal cells, padding insets its children. `cydui_next_width/height/fill/stretch/disabled` apply to the next widget or container only and are cleared at the start of every frame.
- *Fill (the frame of delay):* `fill` children share the space left on the main axis. How many there are and how much the others take is only known at the end of the container, so each container keeps it in the state table (keyed by its position in its parent) and the next frame uses it. The first frame takes what is left; when the numbers change `cydui_ui_end` returns true, so the layout settles on the next frame even if the application only redraws on demand. The remainder of the division goes to the first sharers.
- *Limits (CT-02):* 8 nested containers; a deeper one is ignored together with its end, an end without a begin or of the wrong kind is ignored, containers left open are closed at the end of the frame, each with `CYDUI_ERR_LAYOUT`. A `break` out of a `CYDUI_ROW(ui) { ... }` skips its end and is caught the same way. Grid columns are clamped to 1..64.
- *Positions are signed:* inside a scrolled area a widget is often above the top, so cursors and origins may be negative (they are clamped to the `int16_t` range, not to 0; sizes are never negative). A first version clamped them to 0 and everything after the first child above the top landed in the wrong place; it was found when the scroll golden was looked at again, and a test now compares scrolled content, pixel by pixel, with the unscrolled content moved up.
- *Alignment (the same mechanism as `fill`):* `cydui_set_cross_align` puts each child at the start, middle or end of the container across its main axis (a label centered next to a 32 px button), `cydui_set_main_align` puts the whole group (OK/Cancel pushed to the right); the default is the start, so nothing changes for code that does not use them. The container remembers the size of its content from the previous frame in its state entry (`c` and `d`), so the first frame sits at the start and `cydui_ui_end` asks for another while it settles. The measure is taken where the cursor put the children, not where they end up, so the shift cannot feed back into it (ten stable frames are tested). Nothing moves before a size is known, the main axis needs a container with a size of its own (`next_width`, `stretch`, `fill`), a container that is a child of an aligned one is placed by the size it had (so it keeps a state entry too), and grids ignore both. Nested levels settle in at most one frame each.
- *Cards:* `cydui_begin_card`/`cydui_end_card` open a padded column and paint the theme's `PANEL` exactly as big as the content, **in the first frame**: the panel is painted when the card ends and moved behind the children by rotating the tail of the command list in place (three reversals, no allocation; commands are self-contained, so only their order changes). Cards nest and work inside scroll areas.
- *Quirks, on purpose:* an empty container counts as a child of size zero and so adds one gap; a grid child keeps its own width unless it asks to `fill` its cell.

**Widgets (FR-30).** `label`, `label_wrapped`, `button`, `checkbox`, `toggle`, `spacer`. Buttons, check boxes and switches are at least `style.min_target` (32 px) tall for resistive touch (R-04), a disabled widget is dimmed and neither reacts nor captures the press, text is clipped to its widget, and a widget returns true in the frame of the tap (a held control changes nothing, a release does, once). A frame accepts at most `CYDUI_MAX_WIDGETS` (512) widget calls; the rest do nothing and raise `CYDUI_ERR_TOO_MANY_WIDGETS` (AB-07). Widgets measure, place and react; what they look like is the theme's.

**More widgets (FR-31, FR-32).** `slider` (an `int32` range, 20 px knob, a touch area 4 px wider than the track at each end, `CYDUI_CAPTURE` so the knob follows the finger off the track, `int64` math so the whole `int32` range works, an empty range disables it), `progress` (8 px, value and max clamped) and `tabs` (up to 8 equal tabs; the choice is already drawn in the frame of the tap; every tab has its own id so equal labels are fine). The knob geometry (`cydui_slider_knob_x`, `cydui_slider_value_at`) is public so the widget and every painter agree.

**Themes (FR-50..52, FR-54, NFR-43, CT-09).** `include/cydui/theme.h`, `src/theme.c`, `themes/`. A `cydui_theme` is a palette and metrics (`cydui_style`), a table `table[kind][selected][state]` of `cydui_wstyle` (fill, border, text and accent colors, border width, radius, shadow) and an optional painter per widget kind. Kinds: button, check box, toggle, slider, progress, tab, panel, scroll bar. States: normal, hover, pressed, disabled, focused (the library produces normal, pressed and disabled today) and the `selected` bit (checked, on, the active tab). The **default painter is driven by the table** (antialiased corners, outline, a soft shadow made of stacked translucent rounded rectangles, text), so a new look is usually just a different table (NFR-43); a painter of one's own may call `cydui_paint_default` and add to it, or draw everything. `cydui_theme_validate` accepts a theme if its font is usable (everything else is safe with any value, a NULL painter means the default, a kind or state outside the table means the plain one); `cydui_set_theme` refuses an invalid theme (`CYDUI_ERR_BAD_ARG`, the current stays) and a valid one swaps a pointer and asks for another frame, without touching the state table. Two themes ship in `themes/` (`clean` and `clean_dark`, one function over a palette, 28 bytes of palette each plus about 0.7 KB of shared code; the table is built in RAM, 1 KB per theme).
- *Check:* one golden per widget kind showing every state with the light and the dark theme **in the same frame** (the theme is switched in the middle of it), so the switch itself is tested, plus the three `ui_*` goldens of iteration 3, which did not change a pixel when the painting moved behind the theme.
- *Cost:* a card with a shadow is eight translucent rounded rectangles; a screen of controls renders in 0.28 ms on a PC and the page with a card in 1.08 ms. The board will decide whether shadows stay (R-02).

**Scrolling and lists (FR-25, FR-33).** `src/scroll.c`. An area is a window of fixed height onto a column that is moved by the offset and clipped; the offset (in 1/256 px), the speed (px/s), the content height of the previous frame and the last clock live in the area's state entry. A drag that began on another widget of the window is taken over *before* the children are built, so no child shows the press in that frame and none clicks; a widget with `CYDUI_CAPTURE` is not taken over, and neither is a press that began outside the window. Letting go coasts with an integer exponential friction driven by the backend clock (the speed is the mean of the recent frames, so it forgets a finger that rests; the release frame, which usually has no travel, says nothing; a gap between frames counts as at most 100 ms; no clock, no coasting), without overscroll, so the same events at the same times always give the same offsets (checked against an independent simulation, across the clock wrap, and mirrored for the other direction). `cydui_ui_end` returns true while anything coasts. `CYDUI_SCROLL_*` are tunable macros (the feel is tuned on the board in It5). The scroll bar is the theme's `SCROLLBAR` painter and only appears when there is something to scroll. A virtual list builds only the rows in `[first, last)`, the content is exactly `count * item_h` (at most `CYDUI_LIST_MAX_PX`, so the offset fits), and the row index is mixed into the ids inside it. Scroll areas do not nest (the inner one is a plain column, `CYDUI_ERR_BAD_ARG`).

**Writing a widget (FR-36).** The widgets of the library are written with the same public functions an application uses (the recipe is in `ui.h`: `cydui_widget_begin`, `cydui_take_mods`, `cydui_id_str` + `cydui_id_claim`, `cydui_label_len`, `cydui_alloc`, `cydui_interact`, `cydui_draw_text_in`, `cydui_state_of`, `cydui_state_get`). `examples/theme-gallery/rating.c`, five stars drawn from a 4-bit mask, is built as its own CMake target that cannot see `src/`, which is how the missing pieces were found: the per-frame limit, the length of a label up to `##`, text clipped to a box, the state of a widget from two flags, and the position of the pointer in the response.

**Threading (CT-11).** The API is not thread-safe. `cydui_ui_config.thread_id` (optional) names the creating task and debug builds flag a call from another one with `CYDUI_ERR_THREAD`. The ESP32 backend will supply `xTaskGetCurrentTaskHandle`.

**Measured (Xtensa, `-Os`, release).** The library is 23.6 KB of code (it was 14.2 KB after iteration 3): `theme` 4.3, `layout` 4.0, `raster` 3.7, `widgets` 3.4, `ui` 2.6, `scroll` 2.4, `ctx` 1.7, `text` 0.7, `font` 0.3, `types` 0.3, `utf8` 0.2, `arena` 0.1 KB; the two `clean` themes together 1.3 KB and the example `rating` widget 0.9 KB (its star is 200 bytes), so NFR-50 (60 KB; 10 KB per theme) holds with room. `cydui_ui` is 1308 bytes (the layout stack is 9 x 92, the input state 292), a state entry 32, `cydui_theme` 1024 (RAM, built at start), `cydui_style` 28, `cydui_wstyle` 12, `cydui_cmd` 36; a UI with 64 commands, 20 strip rows, 512 bytes of text and 16 state entries needs about 14 KB of RAM, nearly all of it the strip. On a PC (`-O2`) the screen of controls of the gallery (38 commands) costs 8 µs in the widget calls and 280 µs to render, the list page (23 commands) 4.5 µs and 136 µs, the page with a card and stars 3.6 µs and 1.08 ms (the shadow). None of this is the board: the 3 ms budget of NFR-03 closes in iteration 5.

## Backends (FR-60, FR-61)
```c
typedef struct {
    void *user; int16_t width, height;
    void (*flush_strip)(user, const cydui_rect *area, const cydui_color *pixels); /* required */
    bool (*poll_event)(user, cydui_event *ev);                                    /* may be NULL */
    uint32_t (*now_ms)(user);                                                     /* may be NULL */
    void (*frame_end)(user);                                                      /* may be NULL */
} cydui_backend;
```
- `flush_strip` receives `area->w * area->h` pixels with stride `area->w`. Today it is always a full-width strip; the rectangle form is what lets the ESP32 backend send dirty regions in It5.
- **Deviations from the requirements text:**
  - `frame_end` was added to FR-60: the SDL backend needs it to present the frame.
  - FR-61's "headless mode with framebuffer hash" is the separate `mem` backend instead of a mode of the SDL backend. It has no dependencies, so every test and local check run uses it; the SDL backend is only the window.

## Text input, popups and the keyboard (FR-34, FR-35, FR-44, CT-02, CT-12)
- **The editing core** (`src/textedit.c`) works on a buffer of the application and knows nothing of the UI: a character is what `cydui_utf8_decode` consumes (an ill-formed sequence is one character, drawn as the fallback glyph), so the cursor, backspace and delete agree with what is on the screen. The cursor is always on the start of a character: after a deletion it is brought back, because deleting a byte between ill-formed bytes can merge them into one character (found by the fuzzer). Inserting refuses what does not fit (the NUL counts, a character is never cut), what goes over `max_chars`, non scalar values, controls (the newline only with `CYDUI_EDIT_MULTILINE`) and bidi marks.
- **Events and focus.** `CHAR` and `KEY` go to a queue of their own that lives for one frame: the focused field reads it, whatever is left is dropped at the end of the frame, so a key typed with nothing focused is not applied later. The focus is one id in the UI; a press that begins elsewhere, or a focused widget that is not called, drops it (the keyboard keeps it).
- **The text field** measures every character by the advance of its glyph (the width of a text does not count the spaces at its end, so `cydui_text_size` cannot be used one character at a time) and draws from the first visible character, so it does not depend on `CYDUI_MAX_STR`. State: cursor and scroll in `a`, `b`; the refusal outline in `c`, `d` (a deadline in ms, or in frames when there is no clock). **The text area** finds its lines in windows of at most `CYDUI_MAX_STR` bytes that start where a line does; Up and Down keep the column in pixels; the empty line after a final newline holds the cursor.
- **Popups** are built where they are called and their commands are moved behind the last one of the frame at `cydui_ui_end` (`cydui__cmd_move_tail`); the clip is reset in them and their container is an "overlay" that takes no room in its parent. The widgets outside do not react because `cydui_interact` looks at whether a popup was shown in the *previous* frame (the ones before the popup in the frame have already been called when it is begun); the cost is one frame, after a popup closes, in which what is under it still does not react.
- **The keyboard** is built at the end of the frame (after the popup moved), while a field has the focus: rows are strings of UTF-8 characters, a few keys are special (Shift for one capital, the pages, Backspace that repeats after 500 ms, Ok = Enter, hide). Its keys use `cydui_interact` and put their events in the queue of the next frame; what is under it does not react (the state of the previous frame, as for the popup). It is 143 px tall on 240; a field that is tapped or edited inside a scroll area is scrolled to stay above it (`cydui__scroll_reveal`).
- **Not done:** long press for accents, Tab navigation, selection, copy and paste, the blinking of the cursor, a field that grows with its text, and the QR code / web page for typing from a phone (the applications, with Wi-Fi).

## Animation, effects and the themes (FR-07, FR-50, FR-53..55, CT-08, R-02, R-08)
- **The clock** is the backend's `now_ms`, read once per frame (`cydui_now`). Without one nothing animates: every value is its target at once, which is why every golden of the themes without a duration is unchanged by animation. A made-up clock (the rig, the gallery's hashes) makes a frame with animation as reproducible as one without.
- **Easings** (`src/anim.c`) are integers in 12 bits (`CYDUI_ANIM_ONE` 4096), with 64-bit intermediates: quad, cubic, out-back (the constant 1.70158 in fixed point) and out-elastic (`1 - (1 - t)^4 cos(2.5 turns * t)` with a quarter-wave sine table of 65 entries). All of them start at 0 and end exactly at one.
- **A tween** is one state entry (`from`, `to`, start, curve and duration) under an id of its own (the id of the caller mixed with a salt), so it does not touch the state of a widget with the same id; a new target goes on from the value the tween has. It takes a free or an expired entry and never replaces another one: the fuzzer found a scroll area that never settled because its entry had been taken, and a tween of the application fighting the look of a widget over one id. With no free entry the value is the target at once. At most 16 move together and `cydui_ui_end` returns true while one does; when it returns false a loop may sleep (CT-08, AB-08).
- **Looks over time.** A theme with `style.anim_ms` > 0 makes buttons, check boxes, switches and tabs go from one look to another: the widget tweens a 0..1 value along its axis (pressed or selected) and gives the painter `mix` and the look it comes from; `cydui_paint_look` blends the colors and interpolates the numbers, and the default painters place the knob of a switch and the underline of a tab by `cydui_paint_amount`. A custom painter that ignores `mix` just draws the target. The dimming of a popup fades in each time it opens.
- **The post-effect** (`cydui_post_effect`) is called by `cydui_end_frame` for every strip that is sent, between the drawing and the transfer. Its `key` is mixed into the hash of the strip, so a dirty-region frame resends exactly the strips whose key changed: static scanlines return a constant, a glitch returns another number only for the strips under its bands. The rule that the effect depends on the absolute row and the clock only is what keeps the picture independent of the strip height and equal on the board; the fuzzer compares three strip heights, with and without dirty regions and two buffers, with an effect that follows the clock.
- **`retro`** (`themes/retro.c`): a table of 16 colors and painters for the edges: a raised or sunken slab is a stack of five rectangles, each a pixel smaller than the one below (the keyboard on the screen stays in 320 commands). The font is `cydui_mono_16`, Liberation Mono rendered at one bit per pixel (`fontgen.py --hinting mono`).
- **`cyberpunk`** (`themes/cyberpunk.c`): a table, a painter that adds three translucent rings round a pressed, selected or focused widget (their strength follows the look transition), a progress bar that is a gradient, and the post-effect: scanlines (a quarter off every other row with one mask, no multiplication), a glitch (three bands of 3 to 11 rows rotated sideways in place, every 2.4 s for 120 ms, another set every 40 ms) and a sweep that draws the screen from the top in 360 ms when the theme comes in (`cydui_theme_age`). `CYDUI_FX_LOW` keeps only the scanlines, `CYDUI_FX_NONE` only the colors.
- **Shadows.** A card or popup shadow is four layers of alpha 16 (two pixels of spread each). Eight layers of alpha 8 rounded so differently in the 5 bits of red and blue and the 6 of green that a shadow over a dark page turned green; the larger step keeps the proportions and costs half the drawing.
- **Not done:** an entrance animation per widget, a blinking cursor, a Kconfig default for the level of effects, looking at the effects on the real panel.

## The ESP32 backend (FR-62, FR-63, FR-05, FR-42, FR-43, CT-06, CT-13..15)
`backends/esp32/`, built by the root `CMakeLists.txt` as an ESP-IDF component. Everything that can be decided without hardware is plain C and tested on the PC: `touch_filter`, `touch_cal`, `latency` and the pin rules (`pins.h`).
- **Display:** SPI2 with DMA queued transactions; the strip is byte-swapped in place and sent while the next one is drawn (`strip_buffers = 2`); `flush_strip` does not return before the previous transfer ended and `frame_end` waits for all. The backlight is a PWM (LEDC), switched on after the first frame. Controller, pins, clock, inversion, BGR and rotation (0 or 180) are Kconfig.
- **Dirty regions:** the core hashes the commands that touch each strip (FNV-1a, 64 bits, bounded by the clip; text by content, bitmaps by pointer) and draws and sends only the strips whose hash changed; `cydui_invalidate` forces all. The application provides `dirty_mem`.
- **Touch:** a task of its own samples the XPT2046 (asleep on the pen interrupt, every 10 ms while held), so the touch does not depend on the duration of a frame. Per burst: the first conversion after a channel change is discarded, a trimmed mean, rejection of spread, pressure hysteresis, debounce, confirmation of jumps. The result goes through `touch_cal` (affine, least squares over five targets) to a queue that `poll_event` reads; `cydui_esp32_wait` sleeps until an event is queued.
- **Calibration:** `cydui_esp32_calibrate` shows five targets, fits the map and refuses it when a target is further than `CONFIG_CYDUI_ESP32_CAL_MAX_RESIDUAL` (12 px) from where the map puts it or the matrix is degenerate (up to three tries). It is stored in NVS with a magic and a CRC32; one that fails the check is ignored and the default map of the CYD is used.
- **Time and failure:** the frame budget (`frame_budget_ms`) skips the widgets still to be called; the task watchdog is subscribed by `cydui_esp32_init` and fed at the end of every frame and in `wait`; transfers and waits have timeouts. Latency of the last 128 presses is kept and shown by the gallery (`cydui_esp32_latency`).
- **Done in It7:** the renderer is 2 times faster for a full frame (11.5 ms, `09-hardware-notes.md`). **Not done:** rotation 90/270.

Updating a golden: run `CYDUI_UPDATE_GOLDEN=1 ./build/tests/test_golden`, **open the PNGs first**, then commit the changed `.hash` files together with the code change that caused them.

Test-quality note: the unit tests and fuzzers were checked by breaking the code on purpose in all four iterations, about 40 deliberate bugs in the rasterizer, the UTF-8 decoder, the font module and the text code, each of which must make a test or the fuzzer fail. Several first attempts survived and each hole was closed by a specific test:
- It1: breaking the AA corner bias (the tests only checked symmetry, hence the area tests), and a fuzz harness that did not find an injected strip bug until its parameter generation was rewritten.
- It3 (about 130 mutations of the UI code): the id check hash was never tested for real, a one-byte-per-integer id passed because the values differed in the low byte, a release outside the widget but inside the slop was taken for a tap, a press was claimed by the pointer instead of where it started, queue overflow policies had no test, the width of a padded container was not measured, two sibling containers could share their `fill` state, and one real bug: `shown_len` read a byte past a label that fills `CYDUI_MAX_STR` exactly. The fuzzer needed the same lessons again (see its commit): separate memory objects for ASan, sizes from the input, a repeating vocabulary, an oracle for logic errors, seeds that reach the corners.
- It4: a mutation round of 552 operator mutants over the new code, run on four copies of the tree, took 155 survivors down to 104; what remains is equivalent (a `>=` against a `>` where the result is the same), visual tuning constants and zero-size boundary cases. It also showed that the layout clamped positions to 0 (see "Positions are signed"), that the sanitizer builds let undefined behavior print and go on, so no test would ever notice it (they now use `-fno-sanitize-recover=undefined`), and that a golden I had accepted showed a wrong layout and I had called it plausible. The fuzzer found 9 of 12 injected bugs; the three it cannot find are a behavior rule (nested scroll areas), an unreachable division and an offset cap that needs tens of thousands of frames, now unit tests. Such rounds are too slow for what they find, so from here on mutation is limited to a handful of mutants in genuinely new logic.
- It2: a filter boundary one code point off (hence real glyphs on both sides of every range), a culling distance that was too small (hence fonts whose ink lands far from the line box, on screen), a string that was not copied (the overwriting buffer must differ visibly), a blank-glyph rule, and again a fuzz harness that found nothing until it got seed inputs and a mild mode for the generated fonts.

## Known limits and follow-ups
- Line rasterization uses `int64_t` math for the pixels near the segment (1.2 ms for a 2 px diagonal across a strip on the board); lines are rare (the tick of a check box), so it was left. A rounded rectangle with a big radius still computes every pixel of its arcs (the fuzzer makes some that take seconds); the arcs of the widgets of the themes are small.
- Bitmap data for `RGB565` is read with `memcpy`, so unaligned data is fine; the A4 reader assumes the layout above.
- Text: no kerning, whole-pixel advances, no real bidirectional text or shaping (the bidi marks are drawn as boxes, not applied), no ligatures, no ellipsis. The 12 px size is the most sensitive to the missing kerning.
- FR-13 (icon fonts) is only partly done: `fontgen.py` takes any TTF and any code point range, so an icon font works the same way, but no icon set is shipped yet.
- UI: no hover and no navigation between widgets by keyboard (Tab), scroll areas do not nest and scroll vertically only, a list scrolls over at most `CYDUI_LIST_MAX_PX` (4 194 304 px), alignment needs one frame to settle, and a shadow costs four translucent rectangles.
- Animation: a tween needs a free entry of the state table (with the table full a widget just changes at once) and every widget of a theme with a duration uses one, so an application with many widgets on a screen should give the UI an entry for each (32 bytes). The effects of a theme need a clock in the backend. Rotation 90/270 is not done.
